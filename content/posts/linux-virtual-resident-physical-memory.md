一个程序的虚拟内存有几 GiB，RSS 只有几百 MiB；把所有进程的 RSS 加起来，又对不上系统的已用内存。到底哪个数才表示“用了多少内存”？

**这些数字回答的是不同问题：虚拟内存大小描述地址空间，RSS 描述进程映射中驻留的内存，系统物理内存统计描述整机 RAM 的使用情况。** 如果不先确定统计范围，“内存占用”就很容易成为一个含义不明的数字。

> 源码基线：openEuler 内核 `OLK-6.6` 分支，提交 `458474c39f01`，Makefile 版本为 `6.6.0`。本文数值均为便于理解的假设算例，不是实测结果。默认讨论普通 RAM 映射；HugeTLB 等特殊统计在后文单独说明。

## 1. 三个视角，三种问题

| 视角 | 主要问题 | 常见观察入口 |
| --- | --- | --- |
| 虚拟地址空间 | 这个进程建立了多大范围的地址区域？ | `VmSize`、`maps`、`smaps` 的 `Size` |
| 进程驻留内存 | 该进程的哪些映射当前有驻留内存？ | `VmRSS`、`smaps` 的 `Rss` |
| 系统物理内存 | RAM 被哪些对象使用，还有多少空闲或可用空间？ | `/proc/meminfo` |

此外，还有两个常用于进程归因的量：PSS 按共享情况分摊驻留页，USS 通常用来表示未与其他映射共享的驻留部分。它们帮助解释“这部分内存算谁的”，也不能替代整机统计。

## 2. 虚拟内存大小：地址区域有多大

虚拟内存首先是一套地址转换、保护和按需管理机制。监控工具里所谓“虚拟内存大小”，通常指进程地址空间的规模，例如 `/proc/<pid>/status` 中的 `VmSize`。

它包含代码、共享库、堆、栈、匿名映射和文件映射等已建立的区域。**它不是 CPU 理论上能表达的整个虚拟地址范围，也不是已经分配的物理内存。**

一个映射区间可能只有部分地址实际建立了驻留页映射。进程还可能建立暂时不可访问的保留区域；这类地址空间仍可以计入虚拟大小。

例如，程序用普通私有匿名 `mmap` 建立 1 GiB 区域，没有要求预先填充：

| 阶段 | 这段映射的虚拟大小 | 对 RSS 的典型影响 |
| --- | --- | --- |
| 建立区域但尚未访问 | 1 GiB | 不会因此立刻增加 1 GiB |
| 逐页写入其中 64 MiB | 仍为 1 GiB | 相关匿名页驻留后，通常增加约 64 MiB |
| 解除整个映射 | 这段区域消失 | 对应驻留映射被移除 |

表格只描述这段区域的变化。真实进程还有代码、栈等其他部分；THP、缺页路径和并发回收也会影响具体数值。

“逐页读取”也不能直接替代“逐页写入”：匿名读访问可能使用共享零页，并不一定为每个地址分配独立的私有物理页。

虚拟内存更不能理解为“RAM 加 Swap”。Swap 是某些数据的换出后备存储，而虚拟地址空间还可以包含尚未触碰的区域、文件映射等。地址空间大小与 Swap 容量没有这样的简单等式。

## 3. RSS：哪些映射当前驻留在内存中

RSS 是 Resident Set Size，即驻留集大小。它从进程映射的角度统计当前驻留内存，既包括私有匿名内存，也包括驻留的文件映射与共享内存。

本地 `fs/proc/task_mmu.c` 的 `task_mem()` 输出 `VmRSS` 及其组成部分：

```text
VmRSS = RssAnon + RssFile + RssShmem
```

这里 `RssAnon` 是驻留匿名内存，`RssFile` 是驻留文件映射，`RssShmem` 包括共享匿名映射、tmpfs 等相关驻留内存。字段定义与精度说明可参见 [Linux 6.6 /proc 文档](https://docs.kernel.org/6.6/filesystems/proc.html)。

有三点需要单独记住。

**第一，RSS 不等于程序的堆大小。** 代码、共享库、栈和其他映射都可能参与统计。

**第二，RSS 包括共享页。** 某个页被两个进程映射，各进程的 RSS 都可能计入这页，但 RAM 中的数据没有因此变成两份。同一进程对同一物理页建立多个映射，也可能在映射统计中重复计入。

**第三，RSS 没有覆盖进程带来的全部内核开销。** 页表、内核栈、相关内核对象等并不都计入进程的 RSS。`VmPTE` 是单独观察页表开销的入口之一。

RSS 也不是“当前最活跃的数据量”。一页很久没有被访问，只要仍然驻留并计入映射统计，就可以继续包含在 RSS 里。

## 4. 共享页让 RSS 无法直接相加

假设两个进程有如下驻留数据，每个区域都只映射一次，暂不考虑其他开销：

```text
进程 A：私有 40 MiB ──────┐
                         ├── 共享同一份 20 MiB 物理页
进程 B：私有 60 MiB ──────┘
```

则各项统计如下：

| 项目 | 进程 A | 进程 B | 合计 |
| --- | --- | --- | --- |
| RSS | 60 MiB | 80 MiB | 140 MiB |
| PSS | 50 MiB | 70 MiB | 120 MiB |
| 私有驻留部分 | 40 MiB | 60 MiB | 100 MiB |

这批数据实际占用的不同物理页总量是：

```text
40 MiB + 60 MiB + 20 MiB = 120 MiB
```

RSS 合计为 140 MiB，是因为共享的 20 MiB 被两个进程各算了一遍。

### PSS：对共享部分进行分摊

PSS 是 Proportional Set Size。可以先把它理解为：私有页全部计入，共享页按共享份额分摊。上面的共享 20 MiB 各分摊 10 MiB，于是 A 的 PSS 为 50 MiB，B 为 70 MiB。

更严格地说，实现会依据页的映射计数等信息进行分摊；“按进程数平分”适合理解每个进程映射一次的简单场景。同一进程重复映射、大页统计等情况，需要结合具体实现。

在这个简化算例中，PSS 合计刚好对应这些被映射数据的物理占用。但它仍不包含所有内核内存和未映射缓存，也不意味着遍历所有进程就能获得一个原子、完整的整机内存快照。

### USS：私有驻留部分

USS 是 Unique Set Size。对这里讨论的普通映射，常见计算方法是累加 `smaps` 或 `smaps_rollup` 中的：

```text
Private_Clean + Private_Dirty
```

这些字段中的 Private/Shared 是实际页共享情况的分类，不能只根据 VMA 的 `MAP_PRIVATE` 或 `MAP_SHARED` 标志判断。例如，`MAP_SHARED` 区域的某页如果当前只有一个映射，也可能记入 Private。

USS 有助于观察独有的驻留部分，但也不是“杀掉进程后，系统立刻释放多少 RAM”的精确预测。页可能仍被文件缓存或其他内核引用保留；进程退出还会释放一些未计入 USS 的内核资源。

## 5. 系统物理内存：比进程映射更大的范围

从整机看，RAM 不仅用于进程的匿名页和映射页，还用于文件缓存、slab 对象、页表、内核栈、网络缓冲区等。

其中，**Page Cache 与进程 RSS 可能重叠**：同一份文件页既是文件缓存，也可能被映射进进程地址空间。所以不能使用下面这样的加法：

```text
错误：整机已用内存 = 所有进程 RSS + Cached + Slab
```

这里既可能重复统计，也可能遗漏其他用途。`/proc/meminfo` 的不少字段是从不同维度观察同一批页，例如活跃状态、匿名/文件类型、可回收性；它不是一份所有行互斥的账单。

### MemFree 与 MemAvailable

`MemFree` 表示当前空闲 RAM。`MemAvailable` 是内核对“无需换页即可供新应用使用的内存”的估计，会考虑可回收部分与水位等条件。

因此，一页当前被缓存使用，与它以后可能被回收，是可以同时成立的。`MemAvailable` 中可能包含对这类可回收空间的估计。

| 表达式或字段 | 应如何理解 |
| --- | --- |
| `MemTotal` | 内核报告的可用 RAM 总量，不一定等于硬件安装容量 |
| `MemTotal - MemFree` | 在这个统计范围内，当前没有处于空闲状态的容量 |
| `MemAvailable` | 经过回收潜力等因素估计后，可用于新应用的容量 |
| `MemTotal - MemAvailable` | 基于可用量估计得到的量，不能称为所有已分配物理页的精确总和 |

工具显示的 `used` 还取决于工具版本和计算方式。比较两个工具之前，应先检查字段定义与单位，而不是假设同名列必然相同。

`MemAvailable` 也不保证任意申请成功：高阶连续页、NUMA 放置、Zone 约束、cgroup 限额等仍可能限制具体请求。

## 6. 四种常见变化，应该怎样解释

### 申请变多，RSS 没有同步增长

分配器可能只建立或保留地址空间，尚未为全部地址取得驻留页。这可以是正常的按需分配行为，不能仅凭 VmSize 大就判断物理内存泄漏。

### fork 后，两个进程 RSS 都很大

父子进程可以通过写时复制共享已有页。它们各自的 RSS 可以包含共享部分，实际物理数据却尚未复制两份。

后续写入触发私有复制时，物理占用才可能增长。还要另外考虑 fork 本身带来的页表等成本。

### 页被换出，虚拟地址仍然存在

映射没有解除时，虚拟大小可以保持不变，而驻留部分减少；再次访问可能触发换入。

但不要推导出 `VmSize = RSS + Swap`：未触碰的匿名地址、尚未驻留的文件映射等都不符合这个划分。`VmSwap` 也有特定范围，例如不包含 shmem 的换出占用。交换统计与 RAM 后备存储之间还可能存在 Swap Cache、压缩等关系。

### free 之后，RSS 没有立即下降

用户态分配器可能把空间留作复用，而没有归还内核。即使映射已经解除，相关缓存也可能继续存在。

因此应先辨认对象释放、映射解除、物理页释放分别发生了什么，再判断内存是否泄漏。

## 7. 如何在系统上观察

先记录当前运行内核与基本页大小：

```bash
uname -r
getconf PAGESIZE
```

在 Bash 中，可以先观察当前 shell，再把 PID 替换为实验程序：

```bash
target_pid=$$
rg '^(VmSize|VmRSS|RssAnon|RssFile|RssShmem|VmPTE|VmSwap):' /proc/$target_pid/status
cat /proc/$target_pid/maps
cat /proc/$target_pid/smaps_rollup
rg '^(MemTotal|MemFree|MemAvailable|Cached|Slab|PageTables|KernelStack|SwapTotal|SwapFree):' /proc/meminfo
```

如果没有 `smaps_rollup`，可以查看 `smaps`；这些接口还受内核配置和进程访问权限影响。命令读取的是当前运行系统，不是磁盘上某份源码对应的系统。

观察时按问题选择入口：

| 想知道什么 | 优先观察 |
| --- | --- |
| 哪些地址区域变大了 | `maps`、`smaps` 的区域大小与名称 |
| 驻留增长来自匿名页还是文件映射 | `RssAnon`、`RssFile`、`RssShmem`，再细看 `smaps` |
| 共享页分摊后，各进程占多少 | PSS |
| 哪些驻留页目前没有共享 | Private_Clean、Private_Dirty |
| 系统还有多少使用余量 | MemAvailable，并结合回收、Swap、PSI 等压力指标 |

`status` 的 RSS 使用适合快速统计的计数方式，可能存在精度限制；`smaps` 通过更细的映射扫描提供信息，代价也更高。连续读取几个文件时，系统状态仍可能变化，不应要求不同时间的结果精确对齐。

还有一个版本相关的边界：本地文档明确说明，HugeTLB 的 `Shared_Hugetlb`、`Private_Hugetlb` 由于历史原因不计入普通 `Rss`、`Pss` 字段。分析这类负载时需要单独考虑，不能把普通映射的公式直接套过去。

## 8. 源码里的统计从哪里来

这篇可以沿着“展示字段 → 收集数据 → 解释范围”来读源码：

| 本地源码入口 | 阅读重点 |
| --- | --- |
| `fs/proc/task_mmu.c`：`task_mem()` | VmSize、VmRSS 及其分类如何输出 |
| `fs/proc/task_mmu.c`：`smaps_account()` | 驻留页、共享分摊与 Private/Shared 如何记账 |
| `fs/proc/task_mmu.c`：`show_smaps_rollup()` | 进程各映射统计如何汇总 |
| `fs/proc/meminfo.c` | MemTotal、MemFree、Cached 等整机字段的来源 |
| `mm/show_mem.c`：`si_mem_available()` | 本地分支如何估算可用内存 |
| `Documentation/filesystems/proc.rst` | 字段范围、精度与特殊情况 |

面对“这个程序用了多少内存”时，先把问题补完整：要看地址空间规模、当前驻留映射、共享分摊后的份额，还是整机压力？选对范围之后，数字才有可解释的含义。
