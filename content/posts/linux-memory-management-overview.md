打开 Linux 的 `mm/` 目录，会看到 `mmap.c`、`memory.c`、`page_alloc.c`、`slub.c`、`vmscan.c` 等一大批文件。每个名字似乎都与内存有关，但它们各自负责什么，又如何一起工作？

理解内存管理，可以先围绕三个问题建立框架：**程序看到的地址是什么？实际存放数据的内存从哪里来？空间不足时怎么办？**

本文先把这些问题串起来，建立后续做实验、读源码时可以反复使用的地图。

> 源码基线：本地 openEuler 内核仓库，分支 `OLK-6.6`，提交 `458474c39f01`，Makefile 版本为 `6.6.0`。该分支包含发行版扩展和回合补丁，不能视为未经修改的上游 Linux 6.6。下文主要讨论有 MMU 的常见 Linux 系统；具体行为还取决于体系结构、内核配置和运行参数。本文没有给出实测数据。

## 1. 先区分三个层面

Linux 内存管理同时处理地址、存储和策略。很多困惑，来自把这三个层面混在一起。

| 层面 | 要解决的问题 | 关键概念 |
| --- | --- | --- |
| 进程地址空间 | 哪些地址可以访问？如何找到数据？ | 虚拟地址、VMA、页表、缺页异常 |
| 物理内存与分配 | 数据存放在哪里？如何分配页和小对象？ | Node、Zone、page、Buddy、SLUB |
| 使用与压力管理 | 谁在占用内存？不足时如何腾出空间？ | 匿名页、Page Cache、回收、Swap、OOM |

例如，一个进程申请了一段地址空间，不代表系统已经为整个区间分配了物理内存；系统还有空闲物理页，也不代表任意一种分配请求都能成功。

下面从进程的视角开始。

## 2. 程序拿到的地址，不是物理内存的位置

### 虚拟地址、页表与 TLB

C 程序中的普通指针指向虚拟地址。CPU 访问内存时，通过 MMU 按当前地址空间的映射和权限完成地址转换，最终访问物理内存。

为了按块管理内存，系统把地址空间和物理内存划分为页。基本页大小由体系结构和内核配置决定，常见值是 4 KiB，但不能把它当成所有 Linux 系统的固定值。可以运行 `getconf PAGESIZE` 查看当前系统的基本页大小。

**页表记录地址映射及访问权限，TLB 缓存地址转换结果。** TLB 未命中时，硬件可能遍历页表完成转换；TLB 未命中本身不等于缺页异常。映射缺失或权限不满足等情况，才可能触发需要内核处理的异常。

不同进程里相同的虚拟地址可以对应不同的物理页；多个进程也可以把同一个物理页映射到各自的地址空间。地址隔离和共享内存都建立在这样的机制之上。页表的层级和折叠方式与体系结构有关，详见 [Linux 6.6 页表文档](https://docs.kernel.org/6.6/mm/page_tables.html)。

### VMA 与页表分别记录什么

进程地址空间并非一整块性质相同的区域。可执行文件代码、堆、栈、共享库和文件映射，具有不同用途与访问权限。

Linux 用 `struct mm_struct` 描述一个用户地址空间，用 `struct vm_area_struct` 描述其中的一段虚拟内存区域，通常简称 VMA。同一进程的线程通常共享这个地址空间。

可以这样区分二者：

- **VMA 描述区域规则**：地址范围是什么、是否允许读写、是否关联文件。
- **页表描述地址转换状态**：相应地址是否已有映射、映射到哪里、当前页表权限是什么。

一个 VMA 已经存在，它覆盖的地址却可以尚未建立对应的物理页映射。VMA 允许写入，页表项也可能暂时只读，例如为了实现写时复制。

源码入口是 `include/linux/mm_types.h` 中的 `mm_struct`、`vm_area_struct`，以及管理映射区域的 `mm/mmap.c`。

## 3. 一次内存申请会经历什么

假设程序需要一块较大的内存，可以把过程分成几个阶段。这是典型路径，不是每次申请都会完整经过的固定调用链。

### 第一步：用户态分配器处理请求

`malloc()` 是用户态库提供的接口，并不是一个同名的 Linux 系统调用。

分配器可能直接复用已经持有的空闲空间；需要向内核扩展地址空间时，常见实现会使用 `brk` 或 `mmap` 等接口。具体选择取决于分配器实现、请求大小和运行状态。

因此，不能把每次 `malloc()` 都理解成一次进入内核的物理页分配。

### 第二步：建立地址空间

以普通、没有要求预先填充的私有匿名 `mmap` 为例，内核可以先建立地址区域，等程序实际访问时再处理相应的页。

此时，申请成功主要说明映射请求通过了相关检查，**不意味着整个区间已经拥有驻留的私有物理页**。申请还会受到资源限制和 overcommit 策略等因素影响；承诺量统计与物理页是否已经驻留也是两回事。

### 第三步：访问触发缺页处理

程序访问尚未建立有效映射的地址时，CPU 触发异常，内核判断地址是否合法、权限是否允许，以及应该如何提供数据。

典型的匿名内存处理中，只读访问可能映射共享零页；写入则可能需要分配私有物理页。文件映射可能从 Page Cache 找到数据，也可能需要文件系统读取数据。非法地址或无法满足的权限访问则可能导致信号。

所以，**缺页异常不一定是程序错误，也不一定意味着磁盘 I/O**。它是按需分配、文件映射等机制的一部分。

本地源码的 `mm/memory.c` 中，`handle_mm_fault()` 是通用缺页处理的重要入口；`do_anonymous_page()` 可以看到匿名读访问使用零页、其他路径分配匿名 folio 的处理。入口前还有体系结构相关的异常处理，源码阅读时应区分这两层。

### 第四步：需要时分配物理页，建立映射

内核申请满足条件的物理页，准备数据并更新页表。异常处理成功返回后，程序可以继续执行。

这条主线可以记为：

```text
申请地址空间 → 实际访问 → 必要时触发缺页
             → 找到或分配物理页 → 建立映射 → 继续执行
```

它也解释了一个很适合入门实验的现象：申请一大段虚拟内存之后，RSS 不一定立刻按申请大小增长。

### free 之后，内存去了哪里

`free()` 首先把对象交还给用户态分配器。分配器可能保留它供后续复用，也可能通过解除映射等方式归还内核，因此 `free()` 后 RSS 不一定立即下降。

即使解除了一段映射，对应物理页也不一定马上成为空闲页：共享映射、Page Cache 或其他引用可能仍然需要它。**对象释放、映射解除和物理页释放，是三个相关但不同的动作。**

## 4. 物理内存如何组织：Node、Zone、page

从物理内存一侧看，可以先采用下面的简化关系：

```text
系统内存
  └── Node：体现 NUMA 拓扑
        └── Zone：区分地址范围及管理约束
              └── 物理页：基本管理单位
```

NUMA 系统中，CPU 访问不同节点内存的代价可能不同。Linux 用 `pg_data_t`，也就是 `struct pglist_data`，描述节点。单节点系统也使用这套抽象。

节点中的内存进一步按 Zone 管理。例如，`ZONE_DMA`、`ZONE_DMA32` 与地址可达范围有关，`ZONE_NORMAL` 表示常规内存区域，`ZONE_MOVABLE` 用于主要承载可迁移页的内存区域。实际有哪些 Zone，取决于体系结构、配置和启动参数。

Node 和 Zone 是两个维度：前者关注拓扑，后者关注内存范围及用途约束。Node 不应简单等同于一根内存条，Zone 也不是每个进程各有一套的划分。相关结构位于 `include/linux/mmzone.h`，可结合 [Linux 6.6 物理内存文档](https://docs.kernel.org/6.6/mm/physical_memory.html)阅读。

常规受管理的物理页由 `struct page` 记录状态。这个结构是描述页的元数据，不是页中存放的应用数据本身。

阅读当前源码还会频繁遇到 `struct folio`。folio 把一个或多个连续基本页作为一个整体来管理，大小为基本页的二次幂倍数。可以先把它理解为某些操作采用的整体单位；它并不表示系统不再使用 `struct page`，也不等于所有 folio 都是大页。定义与说明同样在 `include/linux/mm_types.h` 中。

## 5. 分配器为什么不止一个

内核既要分配物理页，也要频繁创建几十字节、几百字节的对象，还可能需要很大的连续虚拟地址区间。这些需求适合不同接口。

### Buddy：提供连续物理页块

Buddy 按 order 管理空闲物理页块。order 为 `n` 的块包含 `2^n` 个连续基本页。例如，基本页为 4 KiB 时，order 0 是 4 KiB，order 3 是 32 KiB。

分配时，可以把较大的空闲块逐级拆分；释放时，如果对应伙伴块满足合并条件，就可以逐级合并。高频的小阶分配还会使用每 CPU 页缓存，不能把每次页分配都想成直接操作 Buddy 空闲链表。

源码主要在 `mm/page_alloc.c`。读分配路径时，要同时留意申请的 order、允许使用的节点与 Zone，以及 GFP 标志。GFP 标志会影响分配范围、能否等待和能否触发回收等行为。

### SLUB：把页组织成小对象

如果一个内核对象只有几十字节，为它单独分配一整页显然不划算。

SLUB 是 slab 对象分配器的一种实现，利用底层分配的页管理和复用多个对象。`kmalloc()` 常用于一般大小的内核内存申请，`kmem_cache_alloc()` 常用于专用对象缓存；SLUB 的主要实现位于 `mm/slub.c`，公共部分在 `mm/slab_common.c`。

这里讨论的是启用 SLUB 的配置，不能只根据仓库里存在 `slub.c` 就断言运行内核正在使用它。

### vmalloc：提供连续虚拟地址

`vmalloc()` 提供连续的内核虚拟地址区间，背后的物理页不要求连续。它通过建立映射把这些页组织起来，主要实现位于 `mm/vmalloc.c`。

| 接口 | 主要对象 | 连续性特点 |
| --- | --- | --- |
| `alloc_pages()` | 物理页块 | 成功返回指定 order 的物理连续页块 |
| `kmalloc()` | 一般内核内存申请 | 返回区域在虚拟地址和物理地址上连续 |
| `vmalloc()` | 较大的内核虚拟区间 | 虚拟地址连续，物理地址不保证连续 |

这几个都是内核接口。用户态程序的 `malloc()` 与它们不在同一层。

## 6. 已经分配的内存，主要用在哪里

### 匿名内存：保存进程运行中的数据

典型的堆、栈和私有匿名映射承载程序运行时的数据。它们没有普通文件中的原始内容可以直接重新读取。

`fork()` 后，父子进程可以先共享相关物理页，通过写时复制（COW）处理后续写入。需要保持父子内容隔离时，再为写入方复制数据；如果已经可以独占使用，也可能复用原页。因此 `fork()` 不等于立即复制全部物理内存。

### Page Cache：缓存文件内容

普通缓冲文件读写通常通过 Page Cache。文件映射也可以使用同一份缓存数据，所以“读文件”和“把文件映射到地址空间”会在内存管理内部相遇。

Page Cache 的干净页如果可以从文件重新读取，并且满足回收条件，就有机会被释放；脏页包含尚未写回的修改，通常需要先完成相应写回，不能直接丢弃修改。

并非所有 I/O 都经过 Page Cache，例如直接 I/O 就有不同路径；私有文件映射在写时复制后，也可能产生匿名页。入门时应先建立典型路径，再研究这些分支。

源码入口包括 `mm/filemap.c`、`mm/readahead.c`、`mm/page-writeback.c`，以及具体文件系统的实现。

### 内核自身也占用内存

页表、内核栈、slab 对象、网络缓冲区和各种元数据同样需要内存。其中一部分可在满足条件时回收，另一部分不能随意回收。

因此，系统内存占用不能只用“所有进程 RSS 相加”解释。进程间共享页还可能被多个 RSS 重复计算；PSS 则把共享页占用按共享比例分摊。

## 7. 内存不足时，内核有哪些选择

### 回收：让一些已用内存重新可用

系统通过水位等机制维护可用页余量。`kswapd` 在后台参与回收；当分配遇到压力且分配上下文允许时，申请内存的线程也可能执行直接回收。这会把回收开销带到申请路径上，表现为延迟上升。

回收会考虑页的使用情况、类型和回收成本等因素。传统 LRU 与可选的多代 LRU 是相关机制，具体使用哪种取决于配置和运行设置。相关主实现位于 `mm/vmscan.c`，缓存再次访问的处理还涉及 `mm/workingset.c`。

Swap 为匿名数据等提供换出位置，使内存中的页在满足条件时可以释放，后续访问再调入。它可以配合压缩机制，不能一概理解成每次都立即写磁盘；`kswapd` 的工作也不仅是换出匿名页。

回收还可以通过 shrinker 等机制释放部分内核缓存。并不是所有已用内存都具备可回收条件。

### 规整：让空闲空间更连续

假设系统还有不少空闲基本页，但它们分散在不同位置。需要较大物理连续块的请求仍可能失败。

内存规整（compaction）通过迁移可移动页，尝试形成更大的连续空闲块。它主要解决连续性问题，不是增加物理内存总容量。相关实现在 `mm/compaction.c` 和 `mm/migrate.c`。

### OOM：特定分配困境下的处理

当相关分配路径无法取得足够进展，并且满足 OOM 处理条件时，内核可能选择受害进程，通过终止它来释放资源。相关实现位于 `mm/oom_kill.c`。

但分配失败不一定触发 OOM：某些请求可以直接失败，高阶请求也可能放弃或回退。回收、规整和 OOM 更不是每次都按固定顺序执行的三级流水线。本地 `mm/page_alloc.c` 的 `__alloc_pages_slowpath()` 展示了这些决策如何受分配条件影响。

另外，memory cgroup 可以限制一组进程的内存使用。即使整台机器还有可用内存，组内仍可能因自身限制进入回收或 OOM。分析时必须区分全局压力与组内压力。

所以，“还有空闲内存，为什么申请失败”至少需要继续追问：**空闲页在哪里？是否连续？这个请求允许使用它们吗？是否受到 cgroup 限制？当前上下文允许等待回收吗？**

## 8. 用几个只读命令，把概念对应到系统

初次观察不需要修改内核。可以先记录运行环境：

```bash
uname -r
uname -m
getconf PAGESIZE
cat /proc/meminfo
cat /proc/buddyinfo
```

再观察一个持续运行、属于当前用户的进程。在 Bash 中，可以先以当前 shell 为例：

```bash
target_pid=$$
cat /proc/$target_pid/maps
cat /proc/$target_pid/smaps_rollup
```

`maps` 展示虚拟内存区域；`smaps_rollup` 汇总映射的内存统计。如果内核未提供该接口，可以查看 `/proc/$target_pid/smaps`。之后做实验时，把 `target_pid` 换成实验程序的 PID。

| 观察项 | 初步解释 | 不应直接推导出的结论 |
| --- | --- | --- |
| `MemFree` | 当前空闲 RAM | 数值小就一定内存不足 |
| `MemAvailable` | 估计无需换页即可用于新应用的内存 | 任意分配都能成功的保证 |
| `Cached` | 包括文件缓存、tmpfs/shmem 等的缓存统计 | 全部可以立即释放 |
| `Slab` | 内核 slab 对象占用 | 全部都是泄漏，或全部都可回收 |
| RSS | 进程驻留内存统计 | 进程独占的物理内存总量 |
| `/proc/buddyinfo` | 各 Node、Zone、order 的 Buddy 空闲块数量 | 包含所有每 CPU 页缓存的完整空闲页清单 |

这些统计是观察入口，不是完整诊断结论。字段定义可查本地 `Documentation/filesystems/proc.rst`；部分进程 RSS 快速统计存在精度限制，需要更细观察时应使用 `smaps` 等接口。

尤其要注意：这些命令观察的是**当前启动的内核**。机器上存在一份 openEuler 源码，并不代表运行系统就是由它构建的。

## 9. 从全景走向源码和实验

第一次阅读，不必沿着函数调用无限展开。先找出每个机制维护的状态、触发条件和预期结果，再用小实验验证。

| 下一步的问题 | 建议入口 | 实验观察 |
| --- | --- | --- |
| 申请地址后，何时获得物理页？ | `mm/mmap.c`、`mm/memory.c` | 匿名映射后不访问、逐页读、逐页写的 RSS 与缺页变化 |
| 为什么小块分配容易，大块分配困难？ | `mm/page_alloc.c` | Buddy 各 order 空闲块分布 |
| 内核小对象如何复用？ | `mm/slub.c` | slab 缓存的对象数量与内存占用 |
| 第二次读文件为什么可能更快？ | `mm/filemap.c` | Page Cache、I/O 与访问耗时 |
| 内存压力为什么带来延迟？ | `mm/vmscan.c` | 回收活动、缺页与应用耗时 |

涉及制造内存压力、修改内核或验证 OOM 的实验，可以放到 QEMU 虚拟机中，并记录运行内核、配置和内存限制。基础观察可以先在现有系统上进行。

这一系列的下一篇，适合从 **“申请了 1 GiB 内存，为什么 RSS 没有立刻增加？”** 开始。它可以把地址空间、缺页、物理页分配这三个层面连接到同一个可观察的过程里。
