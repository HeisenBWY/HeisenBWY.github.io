# 文章研究与写作

## 开始前

1. 检查工作树，保留用户已有修改。
2. 确认文章对应的专题模块和研究问题，避免另建重复条目。
3. 记录本地内核的当前分支和提交号；不要读取、记录或展示 Makefile 版本。
4. 从本地源码、随树文档和官方内核文档收集证据。涉及当前上游状态或外部资料时，只使用一手来源，并把链接放在支持相应结论的位置。

## OS 源码研究基线

当前 OS 专栏默认以 Linux 6.6 为理解机制的起点。按下面四层研究，但不要求为了形式给每层都凑出内容：某一层没有影响文章结论的重要变化时，说明检查范围和“未发现重要变化”即可。

1. **上游 `v6.6` 基础机制**：从 `/home/wangyi/linux/` 的正式标签 `v6.6` 读取源码，解释原始问题、最小模型、关键结构、入口、典型路径和并发约束。不能用该仓库当前检出的 `master` 或 RC 版本代替 `v6.6`。
2. **6.6.y 稳定修复**：检查 `v6.6` 之后进入 6.6 stable/LTS 的主题相关修复，重点关注正确性、安全、竞态和回归。它们属于同一版本线的维护，不与后续主线新特性混写。
3. **openEuler OLK-6.6 增量**：从 `/home/wangyi/openEuler-kernel/` 当前 `OLK-6.6` 基线分析主题相关差异。区分 openEuler 自有修改、后续上游补丁回合、stable 修复回合和来源尚未确认的修改；不能把“`v6.6` 中没有”直接写成“openEuler 原创”。
4. **6.6 之后的上游演进**：从 `v6.7` 检查到研究时最新正式稳定版，必要时再单独观察当前 mainline/RC。只选择会改变机制理解、接口、正确性、性能、可观测性或当前源码阅读方式的提交；RC 内容必须标明尚未正式发布。

先以源码路径和关键符号缩小提交范围，再使用日志、blame、提交说明、邮件列表和官方文档确认语义。不要把 `v6.6..当前版本` 的全部提交写成更新日志。

对文章中展开的重要补丁，尽量回答：

- 原实现存在什么问题，补丁是修复、优化、重构还是新接口？
- 补丁首次进入哪个上游版本，是否进入 6.6.y？
- 修改了哪些关键结构、函数或执行路径？
- openEuler 是否包含；若包含，是直接回合、修改后回合还是独立实现？
- 它是否改变本文结论，对用户或开发者有什么可观察影响？

文章开头的研究基线应列出实际使用的上游标签或提交、6.6.y 检查终点、openEuler 分支与完整提交号、后续上游检查终点，以及是否包含实验。版本号必须在写作当时重新确认，不能从旧文章复制。

## 文章形态

文章需要自然回答以下问题，不要求机械套用固定标题：

- 读者遇到的现象或疑问是什么？
- 最小心智模型是什么？
- 哪些概念容易混淆？
- 本地源码中的关键结构、入口和路径在哪里？
- 哪些行为依赖体系结构、内核配置或运行状态？
- 如何通过只读观察或隔离实验验证？
- 下一篇文章应从哪里继续？

概念关系复杂时，优先给一个小算例、对照表或紧凑文本图。只有图能显著降低理解成本时才使用 Archify。

## Front matter

新文章采用：

```yaml
---
title: "文章标题"
date: 2026-10-02T12:00:00+08:00
description: "一句具体摘要。"
categories: ["OS"]
tags: ["Linux", "内存管理", "内核源码", "openEuler"]
cover: /img/covers/<article-slug>.jpg
---
```

- 日期使用实际写作日期和 `Asia/Shanghai` 时区。标签按内容删减或替换，不要为了形式堆满。
- `title` 用问题式问句，与知识地图中的问题条目对应。
- `cover` 指向 `source/img/covers/` 下的图；未准备封面时省略（回落到主题 `default_cover`）。

## 证据表达

- 文章开头用 `{% note info no-icon %}` 提示块记录源码基线、研究范围和是否包含实测；示例见 `source/_posts/` 既有文章的"研究基线"块。
- 源码路径相对于对应仓库根目录表达；同一路径同时讨论上游和 openEuler 时，明确标注来源。
- 函数名和结构名使用行内代码；只摘录能直接支持解释的短代码。
- "典型路径"不能写成所有配置都固定执行的调用链。
- 引用补丁时给出提交号和首次进入的版本；性能数据要区分补丁作者报告、其他公开测试和本文实测。
- 运行系统与源码树可能不一致。给观察命令时提醒读者先记录 `uname -r`、体系结构、页大小和相关配置。
- 命令默认安全、只读。制造内存压力、触发 OOM 或加载修改后内核的实验放入 QEMU 等隔离环境。

## AnZhiYu 标签语法

Hugo 时代的 `callout` shortcode 已全部替换为 AnZhiYu note 标签，写文章时直接使用：

```markdown
{% note info no-icon %} **研究基线** …… {% endnote %}
{% note warning no-icon %} **常见误解** …… {% endnote %}
{% note tip no-icon %} **实验建议** …… {% endnote %}
```

`type` 可用 `info`、`tip`、`warning`、`danger`。不要只为了增加颜色而添加提示框；一个段落只有在需要读者停下来区分概念、条件或风险时才提升为 note。

## 接入知识地图

在 `source/os/memory/index.md` 找到对应问题，把条目从纯文本改为链接：

```markdown
- [问题标题](/posts/<article-slug>/)
```

 permalink 规则为 `posts/:title/`（见 `_config.yml`），内链注意结尾斜杠。如果研究已经开始但尚未成文，保持纯文本条目。不要因一个问题已有文章就声称整个模块完成。

## 验证

至少检查：

```bash
npx hexo clean && npx hexo server -p 4000
git diff --check
```

再用真实浏览器访问 http://localhost:4000/ 确认：文章渲染正常（note 提示块、代码块高亮与行号、封面图）、知识地图链接可达。除非用户已授权，否则不要提交、推送或发布。
